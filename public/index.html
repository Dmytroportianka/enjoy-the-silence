    Why an OS? Why not just Muse, or just Muse?

    A model is a brain in a jar. Muse is an excellent pair of hands — rented, session by session, on a machine someone else prepared. Neither is a place. An agent that only visits can suggest; an agent that lives somewhere it owns can perceive, act, be checked, and be rolled back. The OS is what turns a smart guest into a resident.

    The 3-minute demo

    1. From the dashboard or CLI, file one work order: “Upgrade yourself and prove it.”
    2. The update-check timer has already noticed a new Muse release and filed the task.
    3. The crew dispatches Muse into an isolated worktree — never the live checkout.
    4. The agent bumps the pin, then runs the pre-push gauntlet: lint, typecheck, unit tests, a shuffled test order, containerized E2E.
    5. NixOS builds a new generation and switches — with the previous generation one rollback away.
    6. This page re-reads the repo and shows the new commit. The system improved itself; the receipts updated themselves.

    Honest boundaries

    This is an agent-operated NixOS, not a new kernel. The infrastructure predates the hackathon and is disclosed as such; the judged artifact is the Muse-powered layer on top. Nothing on this page phones home: the server only parses allowlisted fields (routes, preset commands, binary names, commit subjects) and never serves raw file contents, addresses, or secrets.
