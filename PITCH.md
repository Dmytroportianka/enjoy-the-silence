# Pitch — enjoy-the-silence: a software factory that starts itself

## One line
Clone the template, run the wizard, and a reproducible software factory commissions
itself — OS, self-hosted git, governed agent crew, control room — then give it one
sentence and the crew manufactures it, unattended.

## The problem
Side projects die not from lack of ideas but from the setup tax: every new
workspace needs an OS, a repo host, a dev loop, a review process, and a fresh
briefing for every agent session. The owner ends up doing the careful parts by
hand, re-briefing each time, and trusting a single model to grade its own work.

## The solution
A factory that starts itself and works unattended:
1. **Reproducible base** — NixOS config generated by a wizard (never applied by
   the agent; the owner turns the key). Rollback is a previous generation.
2. **Self-hosted loop** — Gitea on the same machine holds the factory's own
   configs, branches, and PRs; one external mirror so local Gitea is never the
   sole copy.
3. **Governed crew** — thin orchestrator (`src/crew/`) spawns each station as a
   separate agent session: triage → plan → red-team (×2) → build → review →
   visual review → land → retro. QC is always a different context from the builder.
4. **Control room** — dashboard (`dashboard/`) shows tasks, stations, live agent
   output, diffs, consumption, and an Inbox for anything the factory cannot
   settle itself.

The owner's job shrinks to stating the work in one sentence and answering the
questions the Inbox cannot settle itself.

## Why NixOS
Reproducibility and rollback. Same factory on your VM as on the reference machine;
`nixos-rebuild switch` is deterministic; rollback is a previous generation.
The wizard only generates — the owner reviews and applies. Templates cover common
cases; `--special "<cases>"` hands the rest to a Muse builder checked by a
separate QC session.

## Why different agents, models, and effort
Independence is the product. QC/red-team is always a separate session from the
builder; the builder's chain-of-thought never reaches the reviewer.

| Station | Model | Effort | Why |
|---|---|---|---|
| planner | muse-wonder-1.0 | high | Deep reasoning for intent/approach/success criteria. |
| red-team (SME + outsider) | muse-wonder-1.0 | medium | Two independent attackers; judgment, not build depth. |
| sme / coder (review) | muse-wonder-1.0 | medium | Diff review against patterns. |
| builder | muse-spark-1.3 | low → medium → high | Fast early; strong only on escalated retries. |
| coder | muse-spark-1.3 | high | Implementation/rework. |
| outsider | muse-spark-1.3 | low | Cheap independent glance. |
| fixer | muse-spark-1.3 | medium | Mechanical rebase resolution. |
| retro | muse-wonder-1.0 | default | Whole-run review and learning. |

These are the muse defaults. Settings → Model routing can move any station
to another installed CLI (`agy`, `gemini`, `claude`, `codex`) with its own
model. Ordered model presets fail the whole factory over to the next
group when a subscription quota runs out or recent failures reach the
owner's critical rate — each runner is a separate subscription, so quota
stops being a single point of failure.

Effort escalates with attempts, so cost stays low where quality is not at risk.

## Meta tooling
- **Muse is the default brain** in the wizard (`src/wizard.ts`, `MUSE_PRESET`).
  The wizard installs Muse pinned and hash-verified (1.4.10).
- Every station runs as a real headless CLI session with resume where the
  runner supports it (`src/crew/preset.ts`, `src/crew/providers.ts`,
  `src/crew/orchestrator.ts`); muse is the default, not the only brain.
- Token usage is read from Muse's own session logs
  (`readSessionUsage` in `src/crew/preset.ts`), so consumption is measured, not
  guessed.
- The demo's Brain step visibly lands on `muse` as the chosen default.

## The pipeline (one sentence → landed feature)
1. **Triage** — estimates size/risk, picks the lane (fast/standard/careful).
2. **Plan** — planner drafts intent, why, approach, success criteria, prerequisites.
3. **Red-team** — SME + outsider attack the plan; both must pass (written args).
4. **Build** — builder in an isolated worktree; timeout → resume or reiterate.
5. **Review** — coder + QC check the diff against `PATTERNS.md`; REJECT bounces
   the builder with a quoted reason.
6. **Craft gate** (UI/copy only) — closed-set veto: `DEAD-CONTROL`, `FAKE-CLAIM`,
   `GHOST-LINK`, `SCRIPT-PATCH`.
7. **Visual Review** (pages only) — screenshot diffs against the base commit;
   the owner approves or requests changes before anything lands.
8. **Land** — verified branch merges to main (isolated path if main is dirty).
9. **Retro** — retro agent reviews the run and files findings as candidate tasks.

Gates are armed per card; a veto short-circuits before any agent spawns.

## Retro points (the learning loop)
After a task finishes, `sweepRetros` (every 3s tick, 30s settle) runs `runRetro`
with a fresh session. Findings are filed via `fileRetroPoints` as candidate tasks
tagged `retro-point`, appearing in the Inbox for the owner to accept (planning
starts) or remove. "We noticed X" becomes a tracked, reviewable task.

## The demo proof point
The dashboard recording shows a factory that says no to itself: the builder ships
a smoke check that accepts any string; the coder reviewer REJECTs ("weak
coverage"); the builder reworks and pins the greeting; both reviewers pass;
verify gate passes; branch lands; a retro finding is filed. Then the Inbox shows
the candidate retro-point task. A factory that visibly rejects weak work is more
convincing than ten clean landings.

## Architecture in one paragraph
Thin orchestrator (`src/crew/`) spawns each station as a separate agent
session (muse default; other installed CLIs per model preset) with a job
card, worktree, verify command, and gates. Context packs
(`src/crew/context-pack.ts`) assemble role-specific stable context once, cached
by hash. Verification results cached by worktree HEAD. The dashboard
(`dashboard/`) is a React SPA over a Bun server reading the same store, so it
restarts freely and the factory runs headless without it. State lives in
`factory-data/` (tasks, jobs, SQLite dialogue, settings, quota pause).

## Tech stack
- Runtime: Bun, TypeScript, React 19, Vite, Tailwind 4.
- OS: NixOS (reproducible base, template/).
- Agent: Muse (Meta) default brain via `muse exec --json`, pinned &
  hash-verified; stations may instead run agy, gemini, claude or codex
  per model preset (see `src/crew/providers.ts`).
- Storage: plain JSON files + SQLite (dialogue, drafts, scout, imports).
- Verification: Biome + ESLint + tsc + coverage (bun test).

## Alignment
- **Meta tooling**: Muse is the default brain; every station is a real
  `muse exec` session; consumption read from Muse's own session logs.
- **Reproducibility**: NixOS base + generated config + rollback.
- **Governance**: independent QC context, gates, retro points, suppression
  ratchet, `bun run verify` as the only definition of done.
- **Cost awareness**: per-station token accounting, caching, effort escalation.
